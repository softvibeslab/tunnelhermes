Hermes–Cursor Replica Kit v1

Paquete privado de documentación y réplica. Abrir wiki/index.html para navegar sin servidor. La wiki también está en Markdown para importar manualmente a Azure DevOps Wiki, GitHub Wiki u Obsidian. No se creó ninguna wiki remota ni enlace público.

Esta versión es NUEVA y NO sustituye el bridge de origen. Los tests locales usan un runner controlado y no prueban al proveedor LLM ni Cursor real. Ver evidence/validation.txt y wiki/08-evidencia.md.

Inicio rápido

Requisitos: Linux, Python 3.11+, Hermes instalado y configurado, usuario de servicio sin privilegios, perfil dedicado previamente autorizado, proveedor disponible y permisos técnicos revisados. El kit no incluye configuración personal, memoria, repositorios, tokens ni credenciales de modelo.

1. Verificar SHA256SUMS.json con python3 verify_package.py. 2. Ejecutar python3 -m unittest discover -s tests -v. 3. Inspeccionar puertos con ss -lntp y proxy existente antes de reservar puerto. 4. Crear/configurar el perfil dedicado con herramientas oficiales de Hermes; no clonar secretos ni usar default. Revisar hermes profile --help, hermes profile create --help y documentación oficial antes de crearlo. 5. Ejecutar como usuario de servicio: python3 configure.py --state "$HOME/hermes-cursor-state" --profile cursor-bridge --workspace "$HOME/workspace" --port 8797 El workspace debe existir. Se genera un token nuevo que NO se imprime. config.json arranca con policy_reviewed=false. 6. Revisar config.json: proyectos, repositorios exactos y permisos efectivos. policy_reviewed=true es una confirmación del operador, NO un sandbox. Usar cuenta sin acceso a datos de otros clientes, credenciales de repositorio read-only y filesystem de negocio read-only. El directorio del perfil requiere escritura para sesiones; no exponer credenciales de escritura. 7. Iniciar solo después de esa revisión: python3 bridge.py --config "$HOME/hermes-cursor-state/config.json" 8. Verificar GET http://127.0.0.1:8797/health; exponer mediante proxy HTTPS conforme wiki/04-despliegue.md. No cambiar a 0.0.0.0. 9. Provisionar el token de forma privada en el entorno del proceso Cursor como HERMES_BRIDGE_TOKEN y URL HTTPS como HERMES_BRIDGE_URL. No enviar el PAT de Azure DevOps a Cursor. 10. Desde el kit en el equipo cliente: python3 client.py examples/request.json --out output/draft-001.json

El output no se sobrescribe. No hay reintentos automáticos ni deduplicación persistente. request_id correlaciona pero NO garantiza idempotencia. Una respuesta 200 es borrador; evidence_verified permanece false hasta comprobación externa.

Templates systemd y Traefik son ejemplos con sustituciones explícitas, no instaladores ejecutados. No se modifica infraestructura al descomprimir o configurar el kit. El administrador debe instalar y validar esos templates conscientemente.

Arquitectura y alcance

Cursor → client.py → HTTPS/Bearer → proxy del VPS → bridge privado → Hermes CLI → fuentes autorizadas → borrador → revisión humana.

Es un bridge propio, no SSH, VPN, MCP ni API nativa de Hermes. No sincroniza el workspace de Cursor. Se ejecuta una operación enrich_user_story; no hay endpoint de shell arbitraria. TLS termina en el proxy; el tramo backend usa HTTP privado.

Origen observado: https://hermes-harness.iamobilityappsinc.com/v1/enrich-user-story. La réplica usa SU PROPIO dominio y token; no debe apuntar al origen por accidente. El código distribuido es una versión separada con controles adicionales; no fue desplegado sobre el origen.

Límites: un perfil no es aislamiento de seguridad por sí mismo, draft_only no bloquea herramientas, ni una allowlist de nombres impide al agente consultar otras fuentes disponibles. La seguridad requiere usuario/credenciales/montajes/red limitados. No importar memorias o repositorios del origen sin autorización.

Proceso funcional y responsabilidades

1. Negocio/PO presenta una necesidad incompleta. 2. Cursor prepara HU, proyecto, rama y fuentes autorizadas. 3. Bridge valida autenticación, modo y contrato; limita a una ejecución simultánea. 4. Hermes enriquece con fuentes accesibles; identifica vacíos y preguntas para PO, UX, arquitectura, datos, seguridad, desarrollo, QA y DevOps. 5. Se produce un borrador: alcance, reglas, actores, flujos, estados, excepciones, permisos, integraciones, criterios y riesgos. 6. Responsables revisan y aprueban la especificación antes de la HU final. 7. El equipo conecta CP1/CP2/CP3 según sus definiciones oficiales; el kit no inventa su significado. 8. Desarrollo y QA mantienen requisito → riesgo → caso → ejecución → evidencia → defecto → decisión. 9. Negocio acepta o devuelve tras demo y evidencias. Escrituras en Azure DevOps permanecen fuera del bridge. 10. DevOps aplica Quality Gates, artefactos versionados/firmados, CI/CD, cambio, rollback y validación postproducción. 11. SRE observa errores y telemetría; PO mide valor con una línea base y fuentes identificadas. Sentry/analítica son integraciones propuestas, no incluidas en este kit.

El kit implementa el tramo de enriquecimiento, no el ciclo completo. IA propone → herramientas ejecutan → personas autorizadas verifican y deciden.

Contrato del kit e integración Cursor

POST /v1/enrich-user-story con application/json y Authorization: Bearer. Variables cliente: HERMES_BRIDGE_URL y HERMES_BRIDGE_TOKEN, inyectadas por entorno/gestor de secretos, nunca en reglas o prompts. El token no incluye el prefijo Bearer.

Campos requeridos: operation=enrich_user_story, mode=draft_only, request_id y project con letras/números/_/./-, story.title y story.description no vacíos. repo_candidates es lista de strings exactos autorizados por proyecto; si no está vacía, branch es obligatorio. constraints es lista de strings. Campos adicionales no admitidos. Ver examples/request.json y validate() en bridge.py, autoridad ejecutable del contrato.

Respuesta exitosa: schema_version=1.0, request_id, status=draft, mode=draft_only, result (objeto JSON del agente), evidence_verified=false. El objeto result aún no tiene esquema semántico estricto: revisar fuentes y campos requeridos por el negocio. Salida no JSON del modelo: 502, no falso éxito.

Códigos: 400 JSON/transferencia inválida; 401 auth; 404 ruta; 408 lectura de body; 411 Content-Length; 413 tamaño; 415 media type; 422 contrato/allowlist; 429 ejecución ocupada; 500 error interno; 502 Hermes/salida; 503 auth no disponible; 504 timeout. El cliente informa códigos sin imprimir cuerpos sensibles.

La regla .cursor/rules/hermes-bridge.mdc es un ejemplo opt-in para copiar al proyecto autorizado. La invocación depende de las políticas y capacidades de su versión de Cursor; no se configura el IDE remotamente con este paquete.

No hay idempotencia persistente. No reintentar tras timeout sin comprobar ejecución. El cliente espera 420 s, backend 360 s y proxy de ejemplo 390 s; cualquier LB/CDN adicional debe permitir ese presupuesto o requerirá jobs asíncronos.

Runbook de réplica

Preparación

Ejecutar el kit con Python 3.11+ en Linux. Instalar/configurar Hermes consultando https://hermes-agent.nousresearch.com/docs/ y hermes --help. No descargar instaladores a ciegas como parte de este paquete. Crear usuario de servicio sin privilegios y perfil dedicado solo con autorización del administrador del destino. Crear workspace vacío o fuentes autorizadas read-only. El kit NO crea perfiles ni modifica otros perfiles.

Consultar ss -lntp, proxy existente, red Docker y firewall. Evitar puertos ocupados; en origen están reservados 3000/3100/3101/4317/4318/12345. No asumir que 8797 está libre en el destino. configure.py prueba bind, pero hay que verificar listeners de nuevo al iniciar.

Configuración

Seguir README. configure.py genera token nuevo y config sin sobrescribir archivos. policy_reviewed=false bloquea el inicio hasta que el operador confirme revisión. Establecer proyectos y lista de repositorios exactos; no aceptar URLs arbitrarias del cliente. Configurar aislamiento OS y credenciales read-only antes de poner true. La revisión es manual; el flag no verifica permisos por sí solo.

TEMPORALES: configurar scratch en un directorio privado, respaldado por cuota/retención adecuadas. No usar rutas de otros clientes. Hermes puede guardar sesiones/transcripts además del prompt temporal, por lo que se debe revisar retención del perfil.

Red y TLS

Proxy en host: usar bind 127.0.0.1. Proxy Docker: usar gateway privado real de esa red, NO suponer 10.0.1.1; autorizar solo la subred del proxy por firewall. Un contenedor no llega al loopback del host. Nunca publicar el backend directamente. La interfaz privada por sí sola no sustituye al firewall.

Crear A record del subdominio hacia IP pública comprobada del VPS; valor solo IP, sin protocolo ni puerto. Verificar DNS. Reutilizar proxy existente para TLS/443; 80 solo para redirect o ACME si se necesita. El template Traefik requiere reemplazar dominio, entrypoints, resolver y backend. Configurar redirect HTTPS y security headers conforme política del proxy. Validar configuración y red desde el contenedor antes de publicar. No instalar otro proxy si 80/443 ya están ocupados.

Servicio

Adaptar deploy/hermes-cursor.service.example al usuario y rutas reales. Crear scratch y dar acceso SOLO a perfil/estado; ReadOnlyPaths para fuentes. Verificar que hermes_bin sea ejecutable por esa cuenta y HOME resuelva su configuración. Los templates no incluyen secretos. Revisar systemd-analyze verify antes de instalar; después daemon-reload, enable y start con autorización de cambio. No ejecutar templates con valores REPLACE.

Aceptación

Health interno, conectividad proxy→host, HTTPS público, 401 sin token, 422 autenticado con operación inválida, HU sintética, HU con fuentes autorizadas y revisión humana. Verificar inaccesibilidad del backend desde red pública y ausencia de escrituras no autorizadas. Un health exitoso no verifica el proveedor de modelo.

Seguridad y privacidad

No contiene PATs, Bearer del origen, OAuth, .env, memoria, historial ni configuración privada del proveedor. Cada destino genera su token y provisiona sus credenciales de forma privada. No compartir el token del origen.

Controles del código: Bearer con compare_digest, bind privado, allowlist proyecto/repositorio, draft_only obligatorio, tipos/tamaño, un proceso de agente a la vez, timeout, salida limitada, errores sin stderr, temporales eliminados y logging de request_id/status. El ThreadingHTTPServer no es un servidor público de alto tráfico: siempre detrás de proxy con rate limit, límites de conexión y timeout. La limitación del semáforo cubre ejecuciones de Hermes, no todos los hilos HTTP.

Límites explícitos: no sandbox de herramientas; no verificación semántica de fuentes; result sin esquema de negocio estricto; stdout/stderr temporales pueden crecer hasta límites del filesystem durante la ejecución. Usar cuotas/cgroups, cuenta dedicada y monitoreo de disco. No prometer prevención de escritura sin permisos efectivos y pruebas negativas. La revisión policy_reviewed es una atestación manual, no un control automático.

Montar repositorios y documentos read-only; evitar shell/MCP/herramientas con credenciales de escritura y acceso a otros clientes. No heredar entorno de un usuario administrador lleno de secretos. Auditar prompts inyectados, hooks y herramientas. El dato del cliente es no confiable. TLS no evita prompt injection.

Rotación: generar un token aleatorio nuevo en un archivo temporal del MISMO directorio con permisos 0600, vaciar buffers y reemplazar el archivo activo mediante os.replace (rename atómico). No truncar ni editar en sitio el token activo. Actualizar Cursor por canal privado. El bridge relee y valida longitud/permisos en cada solicitud y devuelve 503 si el archivo está vacío, es inválido o tiene permisos abiertos. Probar que el token anterior retorna 401. El cliente rechaza todas las redirecciones HTTP para no reenviar el Bearer a otro origen o degradar a HTTP. Nunca registrar tokens. Proteger también backups y transcripts. El endpoint health solo expone estado genérico.

Operación y rollback

401: comprobar entorno de Cursor, URL, token antiguo, comillas, espacios y doble Bearer. No pegar secretos en soporte. 429: ejecución activa; comprobar estado antes de volver a enviar. 502: revisar proveedor/CLI con logs privados sanitizados; nunca enviar stderr crudo al usuario. 503: revisar servicio/proxy/firewall; NO abrir 0.0.0.0. 504: revisar presupuesto; no duplicar ejecución a ciegas.

Log de aplicación: request_id y código, no HU. Recoger disponibilidad, latencia p50/p95, errores, ocupación, timeouts, costo si está disponible, fuentes comprobadas y aceptación/devolución por PO. No hay backend de métricas incluido. Owner propuesto: DevOps/SRE disponibilidad; responsable Hermes permisos/contexto; QA evidencia; PO utilidad. Asignar personas antes del piloto.

Rollback: deshabilitar solo la ruta del bridge, detener su unidad, revocar token y conservar evidencia sanitizada. No detener Traefik compartido ni alterar otros servicios. Restaurar versión del paquete y contrato previamente aceptados; comprobar health/auth y HU sintética antes de reabrir. El kit no cambia producción en el origen.

Plan y criterios de cierre

1. Alcance: PO/arquitectura aprueban proyecto, rama, fuentes y datos autorizados. 2. Seguridad: cuenta/perfil dedicados, repositorios read-only y sin credenciales de escritura; Seguridad verifica pruebas negativas. 3. Infraestructura: DevOps comprueba listeners, DNS, TLS, proxy y firewall sin impacto a servicios existentes. 4. Contrato: Backend/QA ejecutan pruebas del kit y acuerdan campos de result requeridos. 5. Cursor: líder técnico configura entorno privado, ejecuta HU sintética desde equipo real y guarda evidencia. 6. Contexto real: owner del repositorio verifica frescura, commit, referencias y respuestas sin fuentes inventadas. 7. Piloto: PO/QA aceptan o devuelven, revisan riesgos y pendientes explícitos. 8. Operación: SRE documenta rotación, alertas y rollback; patrocinador decide continuar o detener.

No se asignan fechas ni ROI sin capacidad y línea base. Para medir valor: tiempo desde entrada a especificación aceptada, devoluciones por ambigüedad, porcentaje de criterios verificables y cobertura de trazabilidad con evidencia. Distinguir línea base, propuesta y resultado observado.

La réplica se cierra solo al pasar E2E real en destino. Las pruebas de este ZIP no cierran ese criterio.

Evidencia y límites de validación

El documento documentacion-origen.md conserva la fotografía de validación del origen con su fecha; no se debe tratar como inventario del destino. El kit v1 no fue desplegado en el origen.

Ver evidence/validation.txt para las pruebas realmente ejecutadas sobre este paquete. Tests con runner controlado verifican contrato HTTP y manejo de proceso, NO inferencia real ni acceso a repositorios. Ninguna salida de prueba representa datos del negocio o una respuesta real de Hermes.

Pendiente en destino: instalación como usuario de servicio, proveedor/modelo, E2E desde Cursor, aislamiento de permisos, conectividad/firewall público, TLS y validación de fuentes reales. Templates de infraestructura requieren adaptación y validación en el stack de destino.
